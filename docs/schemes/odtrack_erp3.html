🏗️架构设计

BFoV init → ERP 目标区域三平铺（中央 + 左右环绕）→ ODTrack 逐帧推理（dense temporal token 记忆）→ BFoV 输出。适配层 `integrations/odtrack/`，上游代码零改动。

🔬技术细节

**ODTrack（AAAI 2024）**：自回归（autoregressive）单目标跟踪器。核心创新是把跟踪建模为**多目标联合生成任务**——离线训练时随机从序列中采样 N 个目标帧（含模板帧）组成 batch 并行预测，使模型学会『用前序目标状态预测下一帧』的自回归模式；在线推理时持续用预测结果扩充 token 序列。backbone 为 ViT-B/16（384 输入），dense temporal token 记忆（MEMORY_THRESHOLD=1000）跨帧累积外观。**ERP 三平铺适配（本项目核心工程）**：`np.concatenate((frame, frame, frame), axis=1)` 将 ERP 帧水平复制 3 份（3W 宽）；首帧框 `_tile_box(box, width) = [x % W + W, y, w, h]` 移到**中间副本**——保证目标无论跨不跨经度边界，中央副本内都是无接缝的完整目标；逐帧推理后预测框 `pred[0] %= W` 折回原始宽度。**适配收益**：三平铺把『跨界目标在搜索图内分裂』问题转化为『平移不变』问题，模型无需感知 ERP 接缝。**评测**：OPE 协议，首帧 GT 初始化，`ope_evaluate`（21 点 AUC + dual IoU 双口径）。**配置**：TEMPLATE_FACTOR/SIZE、SEARCH_FACTOR/SIZE 来自 baseline.yaml。上游 py3.8 时代代码经 `_install_compat` 打补丁（torch._six/visdom 桩）。

🧠机理分析：为什么在长处场景有效

**为什么三平铺是 ERP 全景的正确适配**（结构因果）：ERP 的经度接缝（x=0/W 处）会把跨界目标切成两半，任何局部搜索图都会看到『半目标』。三平铺把帧复制 3 份、目标框移到中间副本后，无论目标真实经度在哪，中间副本内的目标都是完整无接缝的——把『接缝问题』转化为『平移问题』，模型完全无需感知 ERP 边界。配合预测框 x%W 折回，输入输出都是标准单目跟踪语义。**为什么 dense temporal memory 是关键精度来源**：ODTrack 的自回归训练使其学会用前序目标状态（含 dense token 序列，MEMORY_THRESHOLD=1000）预测下一帧——长时序列中外观渐变时，记忆持续提供『目标长什么样』的锚定，这是 LightFC（单帧匹配）0.31 与 ODTrack 0.58 差距 27 个点的结构性原因。**为什么官方 130 基线更高（0.5882 vs 0.5792）**：官方数据 1440×720 分辨率低于 360VOT 测试的 4K，目标占比更大、解码更快（29.9 vs 8.99 FPS），且与隐藏测试集同分布——同一方案在目标更清晰时精度自然提升。**局限机理**：失锁后 dense memory 吸收错误外观形成正反馈（污染），无判丢机制导致一路错到底——这是 recapture/自适应状态机的设计动机。

⚖️优缺点

优点

  • 120 序列赛马冠军（0.5792 > UETrack 0.5143 > LightFC 0.3116）
  • 官方 130 序列基线 AUC 0.5882 / 29.9 FPS，验证方案稳健
  • 三平铺适配收益 > backbone 差距：LoRAT 接入 360 微调后仍只有 0.495
  • Docker 断网自包含交付（cu128 镜像，5090 Blackwell 兼容）

缺点

  • 端到端仅 8.99 FPS（瓶颈在 4K 解码 + 整图拷贝 + CPU 裁剪，非模型）
  • 无判丢/重捕获：失锁后时序记忆被污染一路错到底（10 条失锁序列）
  • dense temporal token 长时漂移正反馈
  • 三平铺输入形态与官方隐藏测试分布有 gap（已被官方 130 序列验证覆盖）

精度优先的提交方案；全帧域（360° 全景单目标跟踪）主干。适合作为融合中的精度教师与失锁研究的基座。
