🏗️架构设计

SphericalMemoryTracker：球面状态 + 模板记忆（update_threshold 门控）+ motion_prior。作为 panotrack 原生 tracker 可选接入。

🔬技术细节

**球面状态表示**（panotrack/models/spherical_memory.py + trackers/spherical_memory.py）：以 24 通道特征（channels=24）编码球面局部区域，template_size=64 的模板特征随帧更新。**门控更新**：update_threshold=0.45——仅当当前匹配质量超过阈值才把新帧外观写入模板记忆，防止被遮挡/形变/相似物污染（与 recapture 的 TemplateMemory 门控思想同源）。**motion_prior**：开启运动先验（球面恒速外推辅助搜索中心），结合 redetect_interval=3 的重检测骨架。**配置路径**（configs/grt360_spherical_memory.json）：patch_size=255, sr_ratio=3.0, sr_min_fov=20.0, lost_score=0.25, lost_psr=3.0, lost_apce=0.5, max_lost_frames=30, hp_sigma=3.0, refine=false。**模型文件**：artifacts/grt360_spherical_memory.pt（合成 + 真实冒烟均通过 load）。**局限**：未进入 medium/representative 赛马主线，无全量验证数据支撑。

🧠机理分析：为什么在长处场景有效

**为什么设计方向合理但无数据支撑**（结构性分析）：球面记忆（24 通道球面特征 + 门控模板更新）在理论上有两个正确动机——①ERP 全景的模板更新必须感知球面几何（同一目标在不同经度/纬度外观不同，门控更新避免把旋转后的外观当成污染）；②update_threshold=0.45 的门控防止遮挡/相似物写入记忆（与 recapture 的 TemplateMemory 同源、与 LoRAT 的『模板污染』问题对应）。**为什么没有进入赛马主线**：该方案是 panotrack 原生 tracker（轻量线 numpy/Pillow 依赖面），而赛马主线已切换为 ODTrack/SUTrack/UETrack 等 GPU 学习型跟踪器——其 24 通道手工特征（对比学习型 dense temporal memory）在容量上无法与 ViT 级特征竞争，属于『先验几何 vs 学习表征』路线的落败。**什么场景下它可能有价值**：作为融合中的『几何先验分支』（球面运动一致性 + 门控记忆为判丢提供独立信号），或作为无 GPU 的 CPU 兜底——与 adaptive_spherical 的 SphericalState（球面运动证据）思想同源，后者的实现实际上继承了它的几何洞察。

⚖️优缺点

优点

  • 球面原生记忆设计与 360 域匹配
  • 模板门控更新（0.45 阈值）防污染思想与 recapture 的 TemplateMemory 同源
  • 为答辩提供『自研全景组件』素材

缺点

  • 无赛马数据支撑（未跑 medium/representative）
  • 模型 artifact（.pt）未在结果集中体现收益
  • 与 ODTrack/SUTrack 等主力相比缺验证

🎯适用场景

未验证的探索组件；若 Phase 2 时间允许可作为记忆增强实验对照，否则留作架构叙事。
